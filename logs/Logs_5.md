# 实验记录
## Log 15: hello from user
### 实验目标
- 接着上次进入用户态的地方，让用户程序通过系统调用打印 `hello from user`，然后正常退出。
- 保留当前的单核、单页用户程序设计，用这个最小的完整过程作为项目的阶段性收尾。

上次已经能够 `sret` 到用户态，不过程序只是在地址 `0` 处循环。没有系统调用，也就无法打印结果，只能用 GDB 确认它确实在运行。这次把剩下的返回路径补上。

### 整体流程
用户程序执行 `ecall`，CPU 跳到 `uservec`。汇编保存用户寄存器，切换到内核页表与内核栈，再进入 Go 的 `Usertrap`。

`Usertrap` 先将 `stvec` 改回 `kernelvec`，保存用户的 `sepc`，接着判断陷入原因：
- `8`：系统调用。将返回地址加 `4`，再根据 `a7` 分发请求。
- `0x8000000000000001`：`timervec` 转发的软件中断。清除 `sip.SSIP`，让当前进程 `yield`。
- 其他异常：打印原因、指令地址和 `stval`，结束这个用户进程。

处理完后，通过原来的 `Usertrapret`、`trampoline_call`、`userret` 回到用户态。

这里有个容易漏掉的细节：`ecall` 保存的是这条指令本身的地址。不加 `4`，返回后又会执行同一次系统调用。

### 系统调用
暂时只实现两个接口：

| 系统调用 | `a7` | 参数 | 返回值 |
| --- | --- | --- | --- |
| `write` | 1 | `a0=fd`，`a1=buf`，`a2=len` | 写入字节数；错误返回 `-1` |
| `exit` | 2 | `a0=status` | 不返回 |

`write` 只接受 `fd=1/2`，都输出到串口。未知调用号返回 `-1`。具体实现放在 `kernel/syscall.go`。

虽然参数里的 `buf` 看起来只是一个地址，但它是**用户虚拟地址**，不能在内核里直接解引用。内核页表没有对应的低地址映射。因此，先检查完整范围是否落在 `[0, p.sz)`，再通过 `walkaddr` 检查页表里的 `PTE_V/PTE_U/PTE_R`，取得物理地址后读取。

当前 RAM 在内核中采用恒等映射，所以可以通过这个物理地址输出字符。先检查所有涉及的页，再开始打印，避免错误参数留下半截输出。

### 退出与调度
不能在 `exit` 中直接调用原来的 `yield`，因为它会将进程改回 `RUNNABLE`。这里抽出 `sched`，让两个调用各自决定状态：

- `yield`：设置 `RUNNABLE`，交回 CPU，以后还会继续运行。
- `exitproc`：设置 `ZOMBIE`，交回 CPU，不再返回。

调度器切回自己的栈后，回收用户页、用户页表和 trapframe，将进程槽改回 `UNUSED`。trampoline 是内核共享的代码，不能释放；内核栈预先分配给进程槽，保留供下次复用。

另外补了 PID 分配、trapframe 清零，以及创建失败时的资源回滚。还没有父子进程和 `wait`，因此退出进程由调度器直接回收。

### 中断与锁
重新开启时钟之前，先补了之前锁实现中的漏洞。

原来的 `release` 总会 `intr_on()`。但如果同时持有进程锁和内存锁，释放内存锁时，进程锁还没有释放，这时不能开启中断。现在增加单核 CPU 的 `noff` 与 `intena`，记录关中断层数和最外层之前的状态，最后一层退出时才恢复。

`sched` 还要保存当前执行流的 `intena`，避免切换期间被其他任务覆盖。`Kerneltrap` 在调度回来后恢复 `sepc/sstatus`，让 CPU 返回原来被打断的位置。

目前的定时器路径很明确：M-mode 的 `timervec` 转发为 S-mode 软件中断，因此只开启 `sie.SSIE`。PLIC 和直接的 S-mode 时钟中断暂不启用。

补充修正之前的解释：`sstatus.SIE` 控制的是 S-mode 下的中断。在 U-mode 下，S 级中断还要看 `sie` 中对应中断源是否开启；关闭中断源也不会屏蔽 `ecall`、缺页等同步异常。

### 实际遇到的问题
#### Go 的临时缓冲区
最初在 `sys_write` 里放了一个局部数组，打算复制用户数据后再输出。但 TinyGo 将其编译成了堆分配，链接时报缺少 `runtime.alloc`。当前使用 `gc:none`，没有提供这套运行时接口。

最后改为通过页表找到物理页后逐页读取，不额外引入 Go 堆分配。

#### 用户程序中的字符串地址
单纯用 `la` 获取字符串地址时，发行版的 RISC-V 编译器生成了通过 GOT 读取地址的指令。代码被复制到 VA `0` 后，还在尝试访问内核里的 GOT，结果触发了用户缺页异常。

在用户汇编里加上：
```asm
.option norelax
.option nopic
```
保持本地符号的 PC-relative 寻址，避免对 GOT 或内核 `gp` 的依赖。这样代码与字符串一起搬到用户页后，地址关系仍然正确。

### 实验效果
用户程序先执行 `write`，返回用户态，再执行 `exit`。QEMU 启动输出的最后几行如下：

```text
OK
jump to scheduler...
hello from user
```

用户程序退出，内核继续留在调度器中。这里没有做关机接口，因此 QEMU 需要手动用 `Ctrl-A X` 退出。

### 验证
新增 `make test`，在独立构建目录中运行五个真实用户程序：
- 正常打印：确认只有 `write`、`exit` 两次 `ecall`，且只打印一次。
- 系统调用参数：检查未知调用号、错误 fd、内核地址、trapframe 地址、越界和溢出范围、零长度写，以及返回值与寄存器恢复。
- 时钟抢占：让用户程序长时间循环，确认 QEMU 记录到来自用户地址的 S-mode 软件中断，之后程序能继续执行并退出。
- 非法指令：记录异常并结束进程。
- 访问内核地址：记录用户缺页异常并结束进程。

每项都通过 QEMU 的监控接口检查当前进程已清空、进程槽回到 `UNUSED`，以及空闲页链表是否恢复。测试不会替换正常的用户程序和仓库根目录的内核文件。

本次使用 Go 1.22.10、TinyGo 0.31.2、发行版 RISC-V GCC 和 QEMU 10.2.1，五项检查全部通过。测试输出和中断记录保存在 `build/tests/`。

从最早内核里的 `hello, world`，到这次用户态的 `hello from user`，启动、分页、权限切换、中断、调度和系统调用终于连成了一个完整过程。
